# 취향렌즈 · Taste Lens

Next.js 16 + React 19 + Supabase로 만든 한국어 배달 플랫폼 형태의 음식 취향 추천 MVP입니다.

## 실행

```bash
npm ci
cp .env.example .env.local  # 새 환경에서만. 이 작업 환경에는 실제 프로젝트 값이 설정됨
npm run dev
```

[http://localhost:3000](http://localhost:3000)에서 확인합니다. 프로덕션 모드는 `npm run build` 후 `npm start`입니다. Node.js 22 이상을 사용합니다.

## 직접 테스트

1. 홈 상단에서 내 취향 프로필을 확인합니다. 그 아래 배달·포장 탭에서 카테고리와 세부 메뉴를 선택하고 검색·정렬·찜 필터 드롭다운으로 가게를 살펴봅니다. 비회원도 메뉴를 탐색할 수 있습니다.
2. 메뉴를 담고 장바구니에서 수량을 바꿉니다. 장바구니는 새로고침 후에도 유지되고 다른 가게의 메뉴를 담을 때 교체 여부를 확인합니다.
3. 이메일로 가입하고 인증 후 로그인합니다. 장바구니를 열어 ‘테스트 주문’을 진행합니다. 실제 결제는 발생하지 않습니다.
4. 주문 완료 화면과 주문 내역에서 수량, 배달·포장, 서버에서 계산한 금액을 확인합니다.
5. 홈의 취향 분석에서 두 음식 중 하나씩 10번 선택합니다. 취향 저장 후 상위 5개 추천과 나의 맛 지도를 확인합니다.
6. 추천 음식을 선택하고 가상 식당 3곳을 취향/평점/가격순으로 비교합니다. 리뷰 근거도 확인할 수 있습니다.
7. 취향 분석 이후 테스트 주문을 하고 주문 내역의 ‘취향에 반영하기’로 프로필 변화를 확인합니다. 재주문 메뉴는 더 크게 반영합니다.
8. ‘나의 취향’에서 테스트를 다시 시작할 수 있습니다. 이전 주문은 보존하며 새 취향 학습에서는 제외합니다.

회원가입 확인 이메일은 Supabase 이메일 제공자 설정을 따릅니다. 기본 메일 서비스는 수신 대상 및 발송량 제한이 있으므로 팀 외부 테스터를 받을 경우 Custom SMTP와 Redirect URLs를 설정해야 합니다. 메일 실제 수신까지의 검증은 사용자 확인이 필요합니다. 개발 기본 리디렉션은 `http://localhost:3000`이며 외부 호스팅 시 해당 주소를 허용 목록에 추가하세요.

## 저장된 내용

연결 프로젝트: `epsdbkwcxzlvqowmgaed` (서울 리전). `tl_` 접두어로 음식, 식당, 프로필(온보딩 응답 포함), 식사 기록, 추천 노출, 수용 피드백, 테스트 주문의 수량·방식·금액을 저장합니다. 공개 카탈로그는 읽기만 가능하며 개인 데이터는 `auth.uid() = user_id`로 격리합니다. 서버 권한 상승 없이 SECURITY INVOKER RPC를 사용합니다. 식사 기록과 배치는 프로필 행 잠금으로 직렬화합니다. 테스트 주문 RPC는 사용자별 잠금과 요청 ID로 중복을 방지하고 DB의 메뉴 가격으로 금액을 계산합니다. 한 번에 한 가게, 수량 1~10개이며 배달비는 예시 2,000원, 포장은 0원입니다.

공개 publishable key만 사용하며 service-role/secret key는 앱에 없습니다. UI 추천은 결정적 수치 계산으로 동작합니다. Open-Meteo는 서버 라우트에서 조회하고 실패하면 날씨 보정을 제외합니다. 데이터가 없는 상황에서는 기본 벡터를 그대로 씁니다.

## 데이터 한계

**demo-ready** 상태입니다. 이메일 인증/DB/날씨는 실제 서비스와 연결되어 있지만 식당 72곳, 가격, 평점, 리뷰는 모두 AI가 작성한 합성 실험 데이터입니다. 음식 24개의 벡터도 검증 전 engineering prior입니다. 리뷰 288개에 대한 수동 구조화 claim을 만들었으며 Solar 분석 결과나 인간 검증 정답으로 표시하지 않습니다. 장바구니와 테스트 주문 저장은 동작하지만 실제 배달 접수·결제·플랫폼 식당 연동은 없습니다. 사진은 카테고리 예시입니다. Match %는 만족 확률이 아닌 RMS 거리 유사도입니다.

Solar Pro 4 리뷰 추출, 공개 리뷰 데이터셋 확보, 인간 label 검증과 H1/H2/H3 사용자 실험은 후속 범위입니다. PRD 전체 분석, 수식 해석 및 FR 매핑은 [docs/MVP_SCOPE.md](docs/MVP_SCOPE.md)를 참조하세요.

## 검증

```bash
npm run typecheck
npm test                   # 수치 로직 테스트
npm run test:integration    # 실제 Supabase + 두 전용 테스트 계정 필요
npm run test:e2e            # 웹 서버 + 전용 테스트 계정 + Playwright 필요
npm run build
```

브라우저 실행 전 `npx playwright install chromium`을 사용합니다. `.env.test.local`에 `TEST_EMAIL`, `TEST_PASSWORD`, `TEST_OTHER_EMAIL`, `TEST_OTHER_PASSWORD`를 설정합니다. 실제 사용자의 계정을 자동 테스트에 사용하지 마세요. 통합 테스트는 두 계정의 취향과 식사 기록을 변경하며, E2E는 취향 재설정을 포함합니다.

`tests/rls.integration.ts`는 공개/개인 데이터 권한, 계정 간 접근 거부, 잘못된 벡터 거부, 동시 중복 요청 및 배치 멱등성, 재선택 가중치를 실제 프로젝트에서 검증합니다. `tests/checkout.integration.ts`는 테스트 주문의 서버 금액 계산, 수량 제한, 잘못된 상황 값 거부, 동시 중복 방지와 사용자 격리를 검증합니다. 브라우저 테스트 3개는 손님 탐색/장바구니, 로그인/취향/주문 전체 흐름, 모바일 화면을 검증합니다. 테스트용 계정은 임시 fixture로 생성 후 삭제했습니다. 이메일 전송은 이 fixture 로그인 검증에 포함되지 않습니다.

## DB 재현

`supabase/migrations`의 네 제품 마이그레이션이 스키마와 카탈로그를 생성합니다. `scripts/seed-data.ts`가 `supabase/seed.sql` 및 테스트용 카탈로그를 생성합니다. 이미 데이터가 있는 프로젝트에 seed를 중복 실행하지 마세요.

SQL MCP의 읽기 전용 경로에서는 INSERT가 거절되어 공식 `apply_migration` 쓰기 경로로 적용했습니다. 원격 마이그레이션 이력에는 일회성 테스트 계정 생성/정리 항목도 있습니다. 이 항목은 제품 스키마와 분리된 테스트 준비이며 신규 환경에는 재생할 필요가 없습니다.

증거와 스크린샷: `evidence/`. `.document-driven/mvp-evidence.json`은 자동 검증 증거를 담고 있으며 사용자의 직접 검증자/시각은 확인 전까지 비워 둡니다. 이를 Strict 승인이나 사용자 수락으로 해석하지 않습니다.

참고 앱의 파란색 배달 UI를 참고한 구현 범위는 `docs/MVP_SCOPE.md`, 사진 출처는 `docs/ASSETS.md`, 최신 검증 결과는 `evidence/DELIVERY_VERIFICATION.md`에 기록했습니다.
