# 취향렌즈 Fast MVP 분석 및 구현 범위

원문: taste_lens_PRD_v1.2.md 전체 2,700행. 사용자의 Next.js + Supabase 빠른 MVP 요청을 기준으로 Timely 환경을 Next.js App Router로 대체한다. Strict harness/lock/baseline은 없었다.

## 검증할 핵심 흐름

신규 사용자가 10회 음식 비교를 완료하고 실제 Supabase에 취향과 응답을 저장한다. 24개 음식에서 상위 5개 추천 및 설명을 확인하고 한 음식을 선택해 식당별 취향 적합도를 비교한다. 먹은 메뉴를 실험 기록으로 남기고 일괄 반영한 뒤 재접속해 결과가 유지되는지 확인한다.

| 요구사항 | 구현 결정 |
|---|---|
| FR-01~04 | 방문 화면, 6 coverage + 4 refinement, bounded optimization, radar profile, retake |
| FR-05~08 | 24개 seed, top 5 RMS ranking, 축 차이 설명, 같은 음식 3개 가상 식당 비교 |
| FR-09~10 | Phase 1.5 후속: Solar 키·실제 검증 데이터 미확보. AI 추출을 구현했다고 표시하지 않는다. |
| FR-11~14 | 집/학교/회사/기타, 한국 시간 자동 분류, 도시 기준 Open-Meteo, 기록이 없으면 delta=0 |
| FR-15~16 | 실제 주문이 아닌 사용자 실험 기록. 정상 .10 / 재선택 .18, 명시적 batch 적용, 중복 적용 방지 |
| FR-17~18 | taste-v1.0, profile/food version, 추천 노출 로그 및 피드백 저장 |

## PRD 해석 및 불일치 해결

1. 8.2의 확률식은 RMS 거리이고 8.3 예제는 제곱 평균 거리다. 본문 8.2 및 8.4에 맞춰 RMS 거리로 통일한다. β=8, λ=.05, [0,1] 제약 하에 deterministic coordinate descent를 사용한다. 최적해 보장이나 70% 예측률 달성을 주장하지 않는다.
2. 10회의 음식 선택은 맛 선호만 관측하지 않는다. 음식 친숙도, 질감, 재료 기호의 편향이 있다. 벡터는 가설이며 영양/알레르기/식이 적합성 판단에 쓰지 않는다.
3. Match %는 100×(1-RMS) 유사도다. 선택 확률/성공률이 아니다. UI에도 설명한다.
4. 온보딩은 6축 대비 질문 이후 누적 축 차이가 가장 작은 축을 보완하는 4문항이다. Active Learning 성능을 주장하지 않는다.
5. 주소지 유형만으로 실제 기상 위치를 알 수 없으므로 도시를 별도 선택한다. 상세 주소/위치정보 권한 없이 도시 대표 지점의 실시간 날씨를 조회한다.
6. 날씨별 선험적 매운맛 가산 같은 임의 규칙을 넣지 않는다. 개인 기록의 context 평균과 전체 평균 차이에 PRD 표본수 가중치를 적용한다.
7. 식당, 가격, 평점, 리뷰는 AI가 작성한 synthetic fixture임을 명시한다. 리뷰를 실제 고객 리뷰 또는 human label로 표시하지 않는다. 각 근거의 provenance를 저장한다.
8. 리뷰 percentile은 동점에 mid-rank를 사용하고, 해당 축 근거가 없는 메뉴는 seed vector를 유지한다. 동일 음식 내 비교, delta 최대 .15, unique review 수/(수+10) shrinkage를 적용한다.
9. 재설정은 기존 기록을 삭제하지 않고 profile baseline_at 이후 기록만 학습에 사용한다. 실험 기록과 실제 주문 전환 KPI를 분리한다.

## 의존성 및 경계

Next.js + React + TypeScript. Supabase Postgres의 공개 카탈로그 read-only 정책, 사용자 소유 데이터 RLS. publishable key는 공개 용도이며 secret/service-role 키를 사용하지 않는다. 사용자 선택에 따라 이메일/비밀번호 Auth를 사용한다. 회원가입 확인 이메일 이후 로그인하며, 같은 계정으로 다른 기기에서도 복구한다. 데이터 쓰기 실패 시 저장 성공으로 표시하지 않는다.

## 검증 및 한계

알고리즘 단위 테스트, 실제 DB/RLS 권한 검증, 브라우저 온보딩→추천→식당→기록→배치→재방문 시나리오, 모바일 레이아웃, 프로덕션 빌드. 사용자 20~50명의 H1/H2 검증, H3의 실제 리뷰 기반 ranking, held-out accuracy, p95 전체 API 지연, Solar F1은 이번 자동 테스트로 통과했다고 주장할 수 없다.

전체 제품 단계는 demo-ready: Auth/DB/날씨는 실제 연동하더라도 식당 및 리뷰와 주문 연동이 실험 fixture이기 때문이다. 사용자 검증자와 승인 시각은 사용자 직접 확인 후에만 기록한다.

## 배달 플랫폼 형태 확장 (2026-09-14)

사용자가 제공한 [청아 딜리버리 참고 앱](https://ai.studio/apps/02415713-eccc-43b9-8c6f-7f492dc57fe8)을 브라우저에서 확인했다. 파란색 계열, 주소 선택, 검색, 배달·포장 선택, 음식 사진 배너, 카테고리, 가게 카드, 모바일 하단 탐색을 참고해 취향렌즈에 맞게 구현했다. PRD의 10문항과 6축 추천은 유지한다.

- 손님 탐색: 72개 합성 가게 메뉴 검색, 9개 카테고리, 추천/평점/가격/예상 시간 정렬, 찜하기, 더 보기.
- 장바구니: 한 가게의 메뉴, 수량 1~10개, 삭제, 다른 가게 교체 확인, 기기 로컬 저장. 취향 분석 없이도 탐색하고 담을 수 있다.
- 테스트 주문: 이메일 로그인 후 실제 Supabase RPC로 수량, 방식, 가격, 배달비를 저장한다. DB 메뉴 가격을 기준으로 계산하며 동일 요청은 한 번만 기록한다. 실제 결제는 0원이다.
- 개인화: 10문항 이후 추천과 메뉴별 맛 적합도를 표시한다. 재주문과 명시적인 취향 반영을 연결한다. 수량 여러 개는 동일한 선택 사건 한 번으로 학습한다.
- 범위: 주소는 도시와 집/학교/회사 등 상황 선택이며 실제 배달 주소가 아니다. 가격, 예상 시간, 배달비, 리뷰는 모두 실험용이다. 결제 제공자, 배달 접수, 쿠폰, 실제 가게 데이터 연동은 구현하지 않았다.

이는 사용자의 추가 요청에 따른 화면/테스트 주문 확장이며 PRD에 실제 결제 요구사항이 있다고 해석하지 않는다.

## 홈 프로필 및 주문 탭 개편 (2026-09-14)

사용자 요청에 따라 홈을 저장된 취향 프로필(6축 점수·레이더) → 배달/포장 탭 → 음식 카테고리 → 개별 메뉴 필터 → 검색/정렬 드롭다운 → 메뉴 목록 순서로 재구성했다. 프로필이 없는 사용자는 취향 분석 진입 안내를 표시한다. 정렬은 취향/별점/가격/시간이며 찜한 가게도 드롭다운으로 고른다. 탭 변경 시 현재 검색·카테고리·정렬을 유지하고 장바구니의 주문 방식과 배달비에 반영한다. 기존 추천 TOP 5와 재주문 영역은 주문 목록 아래에 유지한다.
